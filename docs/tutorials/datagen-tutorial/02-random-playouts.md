# Chapter 02 — Seeded random playout driver

## Abstract

This chapter adds the random-playout driver to the `train` crate: two
functions that play uniformly random legal games on the engine board
and sample distinct plies from those games. By the end you will have a
seeded, deterministic source of raw positions, a unit-tested sampling
routine, and the first crate dependency on `rand`.

## Glossary

| Term | Definition |
|------|------------|
| **Playout** | A single complete game generated by making legal moves until the position is terminal. |
| **Ply** | One half-move; `ply i` means the position after the first `i` moves of a game. |
| **`MAX_PLIES_PER_GAME`** | Public constant (`3`) bounding how many positions one playout may contribute to a class bucket. |
| **Dependency island** | The engine crate's rule: no Burn, no `rand`, no I/O. |
| **Class bucket** | A group of samples that share the same tactical label (win, block, quiet) in the quota collector (chapter 4). |
| **Partial Fisher–Yates shuffle** | A variant of the Fisher–Yates shuffle that stops after selecting `k` elements, giving `k` uniformly random distinct indices in `O(k)` time. |
| **`StdRng`** | A deterministic pseudo-random number generator from the `rand` crate; seeded with `StdRng::seed_from_u64`. |

## Context

Chapter 1 added the `train` crate and the [`Sample`](01-the-train-crate.md)
record. A [`Sample`](01-the-train-crate.md) stores a position as stone
lists plus a side to move, but it does not say where positions come
from. This chapter answers that question: random playouts on the
engine board.

The synthetic-data generator in
[`docs/specs/2026-09-27-datagen-tutorial-design.md`](../../specs/2026-09-27-datagen-tutorial-design.md)
uses random legal games to produce natural-looking positions, then
labels those positions with the engine's tactics module in chapter 3
and feeds them into class quotas in chapter 4. The playout driver is
the first piece of that pipeline.

## Mental mapping

### Why the playout driver lives in `train`, not `engine`

The `engine` crate is a dependency island: no Burn, no `rand`, no I/O.
That rule is locked in
[`docs/12-gomoku-architecture.md`](../../12-gomoku-architecture.md) and
[`docs/13-engine-design.md`](../../13-engine-design.md). The engine's
job is to answer rules questions — is this move legal, who won, what
are the legal moves — not to decide which move to play in a stochastic
generator. Randomness is a training-infrastructure concern, so it
belongs in `train`.

The implementation of `random_game` is deliberately small: it collects
[`Board::empty_moves`](../../../gomoku/crates/engine/src/board.rs),
picks one with `rng.random_range`, and calls
[`Board::play`](../../../gomoku/crates/engine/src/board.rs). It
resembles the engine's differential harness (`tests/differential.rs`),
which also plays random legal games, but that harness lives behind the
`testutil` feature and uses compile-time randomness from a `const fn`
Zobrist-style generator. The production playout driver uses `rand`
because it must be seedable from a command-line argument and
reproducible across runs.

> **Excursion — dependency islands and trait boundaries**
>
> Passing `&mut impl Rng` keeps the engine free of `rand` while letting
> `train` use the same `rand` version as `mcts`. The alternative —
> adding `rand` to `engine` and exposing a `Board::play_random` method
> — would violate the island rule and would force every engine caller
> to pull in `rand`. The boundary here is the same one used in
> `mcts`: the search crate owns the RNG, the rules crate owns the
> board.

### Sampling without replacement: partial Fisher–Yates

`sample_plies(game_len, n, rng)` must return distinct indices in
`1..=game_len`. Sorting and rejection sampling would work but is
inefficient when `n` is a non-trivial fraction of `game_len`. The
standard solution is a partial Fisher–Yates shuffle:

1. Build a vector `indices = [1, 2, ..., game_len]`.
2. For `i` from `0` to `k-1`, where `k = min(n, game_len)`, pick a
   random `j` in `i..game_len` and swap `indices[i]` with
   `indices[j]`.
3. Truncate the vector to its first `k` elements.

After step 2 the first `k` positions are a uniformly random subset of
size `k`; the rest of the vector is a shuffle of the remaining
elements, which we discard. The algorithm is `O(game_len)` to allocate
the vector and `O(k)` to shuffle. Because `MAX_PLIES_PER_GAME` is
small, `k` is at most 3, but the routine is written for arbitrary `n`
because later chapters may tune the cap.

> **Excursion — why the range starts at 1, not 0**
>
> A ply index of `0` would mean the empty starting position. The
> datagen pipeline is interested in labelled positions that actually
> arise from play, so the first useful position is after move 1.
> Sampling `1..=game_len` also matches the natural definition of a
> "ply" as the count of moves made so far.

### The per-game sample cap

`MAX_PLIES_PER_GAME = 3` limits how many positions a single playout
can contribute to a class bucket. Without the cap, an unusually long
or tactical game could dominate the dataset: a single game that
reaches a complex endgame might supply dozens of quiet positions and
swamp the win/block positions the network most needs to learn. The
spec in
[`docs/specs/2026-09-27-datagen-tutorial-design.md`](../../specs/2026-09-27-datagen-tutorial-design.md)
calls this "distribution by design": random playouts provide variety,
but quotas and caps keep the class ratios under control. Chapter 4
implements the collector; this chapter only publishes the constant so
chapter 4 can import it.

### `src/lib.rs`

Add one line after the existing module declaration:

```rust

```

No re-export is required; callers use `train::playout::random_game` or

### `src/playout.rs`

```rust
//! Seeded random playout driver.
//!
//! This module plays uniformly random legal games on the engine board.
//! It mirrors the engine differential harness (random legal games) but
//! lives in `train` because the engine crate is a dependency island:
//! no `rand`, no I/O, no Burn.

use engine::{Board, Move, Status};
use rand::{Rng, RngExt};

/// Maximum number of plies sampled from a single game.
///
/// The cap prevents one unusually tactical game from dominating a
/// class bucket in the quota collector (chapter 4).
pub const MAX_PLIES_PER_GAME: usize = 3;

/// Play a uniformly random legal game to terminal; return the move history.
pub fn random_game(rng: &mut impl Rng) -> Vec<Move>;

/// Choose `n` distinct ply indices in `1..=game_len` (uniform without
/// replacement), so one game contributes at most `n` positions.
pub fn sample_plies(game_len: usize, n: usize, rng: &mut impl Rng) -> Vec<usize>;
```

Implementation notes:

* `random_game` loops while `board.status() == Status::Ongoing`, collects
  `board.empty_moves()` into a `Vec`, samples an index with
  `rng.random_range(0..moves.len())`, and plays the chosen move. The
  `expect` is justified because `empty_moves` returns only legal cells
  and the game is not over.
* `sample_plies` uses the partial Fisher–Yates shuffle described above.
  If `game_len == 0` or `n == 0` it returns an empty vector. If `n` is
  larger than `game_len`, the result is saturated to `game_len` plies.
* `rng` is `&mut impl Rng` so tests can pass a seeded `StdRng` and
  production code can pass any `rand` RNG.

### Tests

Inside `#[cfg(test)] mod tests` in `playout.rs`:

1. `random_game_terminates_within_225_plies` — seed `StdRng` with `7`,
   play 100 games, assert each history has length `<= 225`, replay the
   history through `Board::play` and assert every move is legal, and
   assert the final status is not `Ongoing`.
2. `same_seed_gives_same_history` — two `random_game` calls from
   `StdRng::seed_from_u64(12345)` must produce identical histories.
3. `sample_plies_are_distinct_and_in_range` — 200 seeded trials with
   random `game_len` in `1..=225` and random `n` in `0..=10`; assert
   every returned ply is in range, there are no duplicates, and the
   length is at most `min(n, game_len)`.
