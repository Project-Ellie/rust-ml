# Datagen Primer — how synthetic training data works in our Gomoku agent

## Abstract

This document explains the synthetic training-data generator that
milestone 3 builds: why we generate data before any self-play exists,
what a generated training sample looks like, how the generator turns
random Gomoku playouts into labelled positions, and what the `train`
crate must implement. It is a reading document, not a build tutorial;
the step-by-step build tutorial lives in the same folder
([README.md](README.md)).

The document's conclusions, stated up front: the AlphaGomoku lesson is
that a small network can learn Gomoku tactics quickly if it is first
taught on a curated synthetic curriculum. Our generator produces that
curriculum directly from the engine's tactics module: every sample is
rules-true, the class mix is set by quotas, and the storage format
stores positions (stone lists) rather than neural-network planes so
that augmentation and encoding happen on read. The generator is a
single-threaded, deterministic, seeded binary in the new `train`
crate, with no Burn dependency and no coupling to the `mcts` crate.

The document is self-contained: all project-specific terms and all
symbols are defined in the glossary below and again at first use.
Familiarity with basic deep-learning vocabulary (policy, value, held-out
set) is assumed. Where the document builds on other project documents,
it summarizes the needed content at the point of use and lists the
source in the references at the end.

## Glossary

**Symbols used throughout** (also defined at first use in the body):

- `s` — a Gomoku position, represented as stone lists plus side to
  move in the engine's vocabulary.
- `a` — an action; here, a move on the 15×15 board.
- `π` — the **policy target**: a probability distribution over legal
  moves that the network is trained to predict.
- `z` — the **value target**: the expected game outcome from the side
  to move's perspective (`+1` = win, `−1` = loss/block, `0` = quiet).
- `H` — a game history: the sequence of moves that produced a terminal
  position.
- `ply` — the number of moves played so far in a game; a position at
  `ply` is the board after the first `ply` moves of `H`.

**Project and domain terms:**

- **Sample** — one labelled training position: black stones, white
  stones, side to move, sparse policy target, and value target (§3).
- **Position** — a board state expressed in engine vocabulary (`Vec<Move>`,
  `Color`), as opposed to neural-network planes.
- **Planes** — the 17×17×4 tensor produced by `engine::encode`; derived
  from a position, never stored.
- **Win class** — the side to move has at least one immediate win
  (`engine::immediate_wins` is non-empty).
- **Block class** — the side to move has no immediate win, but the
  opponent does, so forced blocks exist (`engine::forced_blocks` is
  non-empty).
- **Quiet class** — neither side has an immediate win on this move.
- **Tactical class** — one of win, block, or quiet.
- **90/10 shaping** — the policy target for win/block positions puts
  90% of probability mass on the tactical moves and 10% on the
  remaining legal moves (§3).
- **Quota** — a per-class collection target: how many win, block, and
  quiet positions the generator must produce.
- **Shard** — one bincode file containing a stream of `Sample` records,
  at most `SHARD_SIZE` per file.
- **Manifest** — the small JSON file next to the shards: seed, quotas,
  class counts, shard list, and workspace version.
- **Zobrist key** — a 64-bit incremental hash maintained by the
  engine's `Board`; identical positions have identical keys.
- **Soundness gate** — the read-time validation that rebuilds the board,
  checks policy masses sum to 1, and checks that win/block argmax moves
  are tactical (§3, §6).
- **Held-out set** — the ~10% of samples reserved for the network
  tutorial's top-1 accuracy benchmark; separated by `zobrist % 10 == 0`.
- **Key-hash split** — a deterministic partition based on board content
  (the Zobrist key), not on position in a file.
- **Playout** — one complete game generated by making uniformly random
  legal moves until the position is terminal.
- **Burn** — the Rust deep-learning framework this project uses
  (pinned to 0.21.0). The `train` crate deliberately does not depend
  on it.
- **Claim labels** — numbered claims carry a provenance label:
  **[paper]** (taken from cited literature), **[derived]** (computed
  from cited values), **[experiment]** (our tuning parameter, to be
  settled by measurement). Unverified claims are recorded in the
  project's honesty ledger (ch. 12) rather than stated as fact.

## 1. Why synthetic data — the AlphaGomoku stall lesson

The AlphaZero algorithm learns by self-play: the network plays games
against itself, MCTS improves the policy, and the network is trained on
the improved policy and the final outcome. In theory this is all that
is needed. In practice, a small network with random initial weights and
no prior knowledge can take a very long time to discover even basic
Gomoku tactics — that an open four must be blocked, that a double
threat wins on the next move, that a fork exists. AlphaGomoku (Xie, Fu,
Yu 2018), the closest prior work to this project, avoided that stall by
using a curriculum: first imitate synthetic attack/defense patterns,
then imitate a rule-based mentor, then run self-play reinforcement
[ch. 12 §3, ch. 14 §5.3].

The lesson is not specific to Gomoku. Any game with sharp tactical
patterns benefits from giving the network a head start on the patterns
it will later refine through search. The head start can come from
human games, from a strong engine, or — as here — from the same rules
engine the project builds anyway. Our engine already contains a
tactics module (`immediate_wins`, `forced_blocks`, and eventually
win-in-2 search) used for MCTS mock evaluation and testing. That same
module can label positions as win/block/quiet with rules-truth
confidence. The synthetic-data generator is therefore a curriculum
substitute for early compute [ch. 12 §3]: it teaches the network the
tactical vocabulary before self-play exists, using a mentor that is "a
few dozen lines of bit math we would build anyway for testing" [ch. 12
§3].

Two consequences follow. First, the generator must be honest about its
source: the labels are rules-true, but they come from a narrow slice of
position space (tactical positions reachable by random play). Second,
the generator must be built and validated before any network is trained
— which is why milestone 3 builds the `train` crate first and defers
Burn to the net tutorial.

## 2. The signal ladder

Chapter 14 §5.2 orders training signals by noise, from cleanest to
noisiest:

1. **Solver-verified labels** — exact, but covering a narrow, weird
   slice of position space (milestone 4's TSS anchor set).
2. **Synthetic tactical data** — the milestone-3 generator: rules-true
   by construction, distribution by design.
3. **Strong-engine records** — strong but stylistic; labels are engine
   moves, not rules-truth.
4. **Self-play bootstrap (`π`, `z`)** — noisiest early, asymptotically
   exact, and the only signal that tracks the agent's own distribution.

The synthetic tier is unique because both halves of its description are
deliberate engineering choices. **Rules-true by construction** means the
label comes from the engine's bitboard tactics, not from a model's
guess. If `engine::immediate_wins` reports that `(7, 3)` completes five,
then playing `(7, 3)` really does win under the project's freestyle
rules (overlines count, draw at 225) [ch. 13 decision 1]. **Distribution
by design** means the generator does not have to accept the distribution
that random playouts naturally produce. Random play yields far more
quiet positions than wins or blocks, so the generator adds per-class
quotas: once the quiet bucket is full, quiet positions are rejected even
though the loop keeps running, and the RNG keeps generating games until
the win and block quotas are satisfied (§4).

The curriculum descends the ladder: clean supervised signal first,
bootstrap taking over as it becomes reliable [ch. 14 §5.3]. Milestone 3
is the synthetic rung.

## 3. The dataset contract

The `train` crate's central type is `Sample`. It stores a position, not
a tensor:

```text
Sample {
    black: Vec<Move>,        # absolute colors, engine vocabulary
    white: Vec<Move>,
    to_move: Color,
    policy: Vec<(Move, f32)>, # sparse shaped target over legal moves
    value: f32,              # +1.0 win, -1.0 block, 0.0 quiet
}
```

### Store positions, not planes

Storing stone lists rather than 17×17×4 planes mirrors the locked
store-games replay-buffer decision [ch. 12]: planes are a derived view
of a position, and storing them would freeze the encoding and forbid
augmentation. The net tutorial will encode each `Sample` with
`engine::encode` and apply one random D4 transform per sample at load
time — augment-on-read, free because the dataset holds canonical
positions only.

The policy target is also sparse. A dense `[f32; 225]` is 900 bytes of
mostly zeros; the shaped distribution is fully described by the
legal-move list with per-move probabilities. The training code scatters
these pairs into a dense target tensor at batch time.

### Three classes, three targets

Classification is determined by the engine's tactics primitives, in
order:

1. `engine::immediate_wins(board, board.to_move())` non-empty → **Win**.
2. Else `engine::forced_blocks(board)` non-empty → **Block**.
3. Else → **Quiet**.

Win takes precedence when both sides have an immediate win, because the
side to move plays first.

Policy targets:

- **Win/Block:** 90% of mass split evenly over the tactical moves, 10%
  split evenly over the remaining legal moves. The 90/10 split is an
  `[experiment]` default: it keeps the tactical moves visible while
  preventing the policy from collapsing to zero entropy.
- **Quiet:** uniform over all legal moves.

Value targets:

- **Win:** `+1.0`.
- **Block:** `−1.0`.
- **Quiet:** `0.0`.

These are exact integers, not approximations. In particular, they are
not the MCTS mock evaluator's `+0.95` / `−0.90` scaffolding values; see
§7.4.

### Quotas

The generator collects positions until per-class quotas are met. The
default quotas are:

```text
--win   20_000
--block 20_000
--quiet 10_000
```

These are `[experiment]` values. The design goal is a tactical dataset
large enough for phase-0 supervised training while keeping generation
time in the "minutes, not hours" range. The win and block quotas are
equal because both classes are tactical and rare relative to quiet
positions; the quiet quota is half the tactical quotas because random
play already produces quiet positions naturally, and capping quiet keeps
the dataset from being dominated by uninteresting positions.

### Zobrist dedup

Each collected position is deduplicated by its Zobrist key. A given
board state enters the dataset at most once. Symmetric duplicates
(rotations or reflections) are *not* rejected, because D4 augmentation
is an on-read concern, not a dedup concern.

### Shards and manifest

Samples are written to length-delimited bincode shard files
(`shard-000.bin`, `shard-001.bin`, ...), at most `SHARD_SIZE = 4096`
samples per shard [experiment]. Each record is encoded with bincode 2
and prefixed with its length as a little-endian `u32`. The manifest
(`manifest.json`) records the seed, quotas, actual class counts, shard
list, and workspace version. The shards are the data; the manifest is
provenance.

### Soundness gate and key-hash split

Before any sample is used for training, the reader runs
`check_soundness`:

- Rebuild the board from the stored stone lists.
- Check that policy masses sum to 1 within tolerance.
- Reclassify the position with the engine and verify that the value
target matches the class.
- For Win, require the policy argmax ∈ `engine::immediate_wins`.
- For Block, require the policy argmax ∈ `engine::forced_blocks`.

The train/held-out split is computed from the Zobrist key:
`board.zobrist() % 10 == 0` → held-out (~10%). The split depends on
board content, not on position in file, so quota ordering cannot leak
correlated positions into both sides.

## 4. Pipeline overview

One seeded generator run executes the following pipeline:

```text
playout → label → collect → write → read → split/report

1. PLAYOUT: random_game(rng)
   Play uniformly random legal moves until the game ends, returning
   the move history H.

2. SAMPLE PLIES: sample_plies(game_len, MAX_PLIES_PER_GAME, rng)
   Choose up to 3 distinct plies in 1..=game_len without replacement.

3. LABEL: for each sampled ply, rebuild the board and call label(board)
   Classify as Win/Block/Quiet; produce the sparse policy target and
   the exact value target.

4. COLLECT: bucket by class, enforce quotas, reject duplicates by
   Zobrist key, skip terminal plies.

5. WRITE: stream samples to length-delimited bincode shards and write
   the JSON manifest.

6. READ: discover shard-*.bin files, decode records, run the soundness
   gate on every sample.

7. SPLIT/REPORT: partition by Zobrist key % 10, print per-class counts,
   ply histogram, and held-out fraction.
```

Every step is deterministic under the RNG seed. The only source of
variation is the random number generator; every branch (bucket full,
duplicate key, terminal ply) is a deterministic function of the board
and the current counters.

## 5. Seed discipline and determinism

Determinism is a first-class property of the generator. One seeded
`StdRng` drives everything: the random games, the ply sampling inside
each game, and any future reader-side randomness. Running the binary
twice with the same `--seed` and quotas produces byte-identical shard
files and manifest. This is verified by the acceptance ritual in
chapter 8: two independent runs are compared with `diff -r` and must
match.

The seed is recorded in the manifest, so any dataset can be regenerated
bit-for-bit. This is consistent with the project's determinism policy
[ch. 12]: generation is pure CPU code, and determinism is promised for
that generation. (Network training, by contrast, is deliberately not
promised to be bit-identical across GPU backends.)

## 6. What this tutorial defers

The datagen tutorial intentionally stops at the edge of the data
pipeline. The following are delegated to later work:

- **Burn, tensors, models, and training loops** — the net tutorial.
  The `train` crate has no Burn dependency in this tutorial.
- **External corpora** — parsing, license screening, and decision-D5
  re-adjudication are deferred to a later addendum. The milestone-3
  acceptance benchmark measures only the synthetic set.
- **D4 augmentation** — implemented in the net tutorial as
  augment-on-read, free because the dataset stores canonical positions.
- **TSS-prover labels** — milestone 4's anchor set; the soundness gate
  here is a warm-up for the stronger gate the TSS labels will require.

One other item is deliberately not deferred: the compact-recorder
precision trap. The net tutorial will train with full-precision
recorders only; `CompactRecorder` is f16 and must not be used for model
records [ch. 11]. The primer mentions it because the datagen pipeline is
what the net tutorial consumes, and the same care extends across the
boundary.

## 7. Common bugs

The following defects are the most common sources of bad training data
in projects of this kind. The tutorial's tests are shaped around them.

### 7.1 Quiet-dominated datasets

Random play spends most of its plies in quiet positions. Without quotas,
the dataset becomes overwhelmingly quiet, and the network under-fits
the tactical moments where games are decided. Quotas are not an
optimization; they are a design requirement that makes the distribution
"by design" rather than "by accident" [ch. 14 §5.2].

### 7.2 Leakage-prone splits

Splitting by position-in-file — "every 10th sample is held-out" — is
easy to implement and easy to get wrong. The quota collector fills
buckets in class order, and consecutive samples often come from the same
game, so a row-based split leaks correlated positions into both train
and held-out. The key-hash split (`zobrist % 10`) removes position-in-
file from the decision entirely.

### 7.3 Scaffolding values leaking into training labels

The MCTS tutorial's `TacticsEvaluator` uses `+0.95` for a win and
`−0.90` for a block. Those constants are search scaffolding: they make
the sign of the value unambiguous in the tree and keep PUCT's
exploration term from drowning the prior. They are deliberately not
exact because the MCTS tests only ask whether the search *finds* the
tactical move. Training labels must be exact `+1.0` / `−1.0` / `0.0`;
copying the mock's scaffolding values into the training pipeline is a
real bug.

### 7.4 Terminal positions entering the dataset

On a board that is already won, `forced_blocks` degenerates: the
winner's five survives any legal placement, so every empty cell appears
to "block" an unstoppable threat. The position would be mislabeled as
Block with a meaningless uniform policy. Worse, the network is never
asked to evaluate terminals — MCTS handles them exactly — so there is
no valid supervision signal. The collector skips terminal plies.

### 7.5 Evaluating training data without a soundness gate

A generated dataset can pass every unit test and still contain corrupted
records: a flipped sign, a halved policy mass, a board that does not
rebuild. The soundness gate is the last line of defense before a sample
enters a training batch. It must be run on read-back and must fail
loudly.

## 8. Summary

- Synthetic tactical data is the curriculum that keeps the AlphaZero
  loop from stalling early; the AlphaGomoku lesson is that a small
  network learns fast when it first sees curated tactical patterns.
- The signal ladder places synthetic data below solver-verified labels
  and above engine records and self-play bootstrap.
- A `Sample` stores positions (stone lists), not planes; the policy is
  sparse, and values are exact `+1.0` / `−1.0` / `0.0`.
- The generator pipeline is: playout → sample plies → label → collect
  with quotas and Zobrist dedup → write shards and manifest → read back
  → soundness gate → key-hash split and stats report.
- Determinism is guaranteed by a single seeded `StdRng`; the acceptance
  ritual verifies byte-identical regeneration.
- The tutorial defers Burn, external corpora, D4 augmentation, and TSS
  labels to later work.
- Common bugs: quiet dominance, leakage-prone splits, scaffolding
  values, terminal positions, and missing soundness gates.
